# 分支管理与提交流程

## 仓库职责

`hexisi-touko/yangtze-ai-gateway-web` 保存完整 New API 管理端，包括 Go 后端、React 前端、数据库迁移、验证脚本和交接文档。客户端仓库独立管理。
当前管理端业务版本为 `1.0.3`。上游 New API 的 VERSION、管理员业务版本和客户端版本分别维护。

## 分支与版本

| 名称 | 用途 | 生命周期 |
| --- | --- | --- |
| `main` | 已验证的完整主线，新成员默认拉取此分支 | 长期保留 |
| `codex/<任务英文名称>` | Codex 辅助开发，例如 `codex/member-archive-fix` | PR 合并后删除 |
| `feat/<任务英文名称>` | 同学开发新功能 | PR 合并后删除 |
| `fix/<任务英文名称>` | 同学修复缺陷 | PR 合并后删除 |
| `admin-v1.0.0` | 初始版：当前管理端与同学修复补丁 | 不可改写的标签 |
| `admin-v1.0.1` | 第二版：成员正文、月度文档、管理员更新日志 | 不可改写的标签 |
| `admin-v1.0.2` | 归档可读性、长正文与构建信息 | 不可改写的标签 |
| `admin-v1.0.3` | 正文、归档、节省金额、推理强度和客户端配置修复 | 不可改写的标签 |

目前不需要另设长期 dev、master 或为每个版本创建永久分支。发布版本用标签和 GitHub Releases 展示，临时开发使用任务分支。
此轮整理是首次把完整源码归并到初始化 main。后续不直接向 main 提交业务改动，统一使用 PR。

## 每次开发

1. `git switch main`，再 `git pull --ff-only origin main`。
2. 创建任务分支，例如 `git switch -c fix/member-archive-export`。
3. 修改对应模块，更新测试。业务有变化时更新 `pkg/adminversion/versions.json`，运行 `node scripts/generate-admin-changelog.mjs`。
4. 核对 `git status` 和 `git diff`，明确选择源码文件提交；避免直接提交全部本地文件。
5. 推送任务分支，发起 PR 到 main。说明触发条件、前后行为、验证结果和部署影响；AI 辅助改动明确说明来源。
6. 至少一位同学审查，验证通过后合并。合并后确认没有未提交工作，删除任务分支。

不要在旧分支继续长期堆积，也不要直接覆盖同学的提交。冲突应在任务分支解决并复测，不强推 main。

## 发布业务版本

先合并到 main，再为通过验证的提交创建 `admin-vX.Y.Z` 标签和发布记录。
版本记录包含业务变化、修复原因、数据库与配置影响、已知限制和验证范围。与上游版本标签区分，业务标签不会触发上游安装包或 Docker Hub 发布。
`admin-v1.0.0` 对应 `c1d04c0`，`admin-v1.0.1` 对应 `f548192`。
之后的仓库说明和验证配置提交不改变第二版的业务功能。标签不改写；后续业务修复发下一个补丁版本。
源码版本发布与云端部署是两步。本次没有连接、备份或切换云服务器。

## 验证与分支保护

新增 `Admin verification` workflow，在 main 推送和指向 main 的 PR 中执行成员分析相关 Go 测试、Linux 构建、前端类型检查、相关前端测试、生产构建与更新日志一致性检查。
保留上游 New API 的原有 CI 和版权内容；管理员业务标签从上游发布触发器中排除。
仓库所有者应在 Settings → Rules → Rulesets 为 main 开启：禁止强推、禁止删除、PR 合并、至少一位审查、要求 `Admin verification / Verify admin source` 检查通过。
当前用于操作的 GitHub 身份拥有写权限，但不是仓库管理员，无法设置这些服务器端保护规则。此项必须由仓库所有者设置，文档规定不能代替实际保护。

## 可提交与不可提交

提交源码、依赖锁文件、Dockerfile、迁移、必要的部署示例、测试和简明文档。
不提交真实 .env、账号密钥、数据库、日志、成员正文、压缩归档、安装包、node_modules、构建产物、缓存和个人 IDE 配置。
保留 New API、QuantumNous 和所有许可证、NOTICE 及第三方版权说明。
